### S023 · Solving mixed integer linear and nonlinear problems using the SCIP Optimization Suite (ZIB-Report 12-27 2012, no DOI or arXiv id)
**Read level**: full. All 25 file pages: abstract and contents (pp. 3–4), §§1–7 (pp. 5–22), acknowledgments and references (pp. 23–25). Console transcripts and code listings were read as text. Figures 1–2 survive as captions only (pp. 7, 17).
**Role**: core · **Coauthors**: Timo Berthold, Gerald Gamrath, Stefan Heinz, Thorsten Koch, Yuji Shinano, all at ZIB (p. 3). The six-author byline is alphabetical and nothing says who wrote what, so the text is read as the group's voice · **Position in trajectory**: Written in July 2012 at ZIB with MATHEON support (pp. 1, 3, 23). A Japanese translation was announced for the RAMP 2012 proceedings (p. 3; INDEX S071, not read). In the skill's Research Trajectory it sits where "MINLP components in SCIP" meets "2012–2016: exact LP": the SoPlex section advertises iterative refinement from the 2012 report by Gleixner, Steffy and Wolter (p. 10; ref. [16], p. 24), and exact integer programming appears as future work (p. 22).

- **D1 Problem and entry point**: The task is to introduce the suite's three tools (Zimpl, SoPlex, SCIP) and to show how they work together to model and solve MIP and MINLP (abstract p. 3; p. 5).
  - The entry is the practitioner's case for MIP (p. 5):
    - linear models with integer variables are easy to understand;
    - solvers handle large models out of the box;
    - the LP dual bound gives "a proven guarantee about the quality of the best found solution", even when a time limit stops the run.
  - The vendors' recorded algorithmic speed-up, a factor of 55,000 over 20 years, is cited from MIPLIB 2010 [22] (p. 5).
  - The conceptual entry is constraint integer programming, motivated by the integration of CP and SAT techniques into MIP (p. 5).
  - Transferable technique: open a software overview with the guarantee the user gets (a dual bound that bounds the gap at any time limit), and list the features after it (p. 5).
- **D2 Core idea and algorithm design**:
  - **SCIP** (pp. 6–7):
    - The design is plugin-based and centred on constraint handlers. Each handler must decide feasibility for its constraint type and may add presolving, propagation, separation and an LP representation (p. 6).
    - SCIP 3.0 has 126 plugins and 26 constraint handlers. Handlers for linear subclasses (knapsack, variable bounds, set packing, covering and partitioning) allow more efficient techniques, and indicator and SOS1/SOS2 constraints are supported (p. 6).
    - Branch-and-price needs only a pricer plugin, and SCIP manages the tree. This is set against commercial MIP solvers, "for which it is not easily possible to locally add variables via callbacks" (p. 7).
  - **Zimpl** (p. 9): statements only add to a model; all computations except a few noted ones use GMP rational arithmetic, so no rounding errors occur during modelling; absolute values and conditional constraints are turned into linear inequalities automatically.
  - **SoPlex** (p. 10): a composite primal/dual simplex; temporary bound shifting instead of an explicit phase one; Forrest–Tomlin or eta updates of the LU factorization; a row representation of the basis for LPs with more rows than columns; long double on request; and, since version 1.7, iterative refinement that computes arbitrarily precise solutions.
- **D3 Problem class and data model**:
  - Classes (pp. 6–7; Figure 1 caption p. 7):
    - LP;
    - MIP with indicator and SOS constraints;
    - MINLP via expression trees, with special support for quadratic, second-order cone, bivariate and absolute-power constraints;
    - pseudo-Boolean optimization;
    - SAT;
    - CP-style scheduling with cumulative constraints.
  - Table 1 lists ten file formats: lp, mps, cnf, opb, wbo, zpl, fzn, pip, cip, osil (p. 11).
  - Worked instances:
    - a 13-city symmetric TSP with the exponential subtour formulation in Zimpl: 78 variables, 8,021 constraints, 154,596 nonzeros, solved by SCIP in under a second (pp. 11–13);
    - MIPLIB 3.0 stein27 (pp. 13–16);
    - a two-variable toy MIP for the C API (p. 17);
    - Netlib capri for SoPlex (p. 20).
  - No correctness argument is made (n/a).
- **D4 Algorithm and implementation design**: No proofs (n/a). The implementation and testing design is worth recording.
  - Debugging and testing (p. 18):
    - a debug build (make OPT=dbg) activates asserts and extra consistency checks, and SCIP_DEBUG switches on debug messages;
    - "a debug solution" can be added in src/scip/debug.h "to ensure that the code does not cut off an optimal solution";
    - make TEST=… SETTINGS=… runs a test set with a settings file and writes .out and .res files; the .res file lists time, nodes and simplex iterations per instance and geometric means over the set;
    - check/allcmpres.sh compares two or more result files.
  - Code quality (p. 22): test suites cover more than 75% of the code; asserts check preconditions and invariants; Makefile targets run valgrind, and the code is checked with the static checker FlexeLint.
  - Parameters: more than 1,400, grouped by component, with emphasis meta-settings (pp. 15, 18–19).
  - SoPlex options: an a posteriori check of solution quality (-q) and basis files for warm starts (p. 20).
  - Footnote 10 fixes the meaning of "proven": solved exactly over the rationals with the gap closed to zero, "not only some small epsilon" (p. 22).
- **D5 Computational evaluation**: None in the sense of card_dimensions: no test set, baselines, metrics or hardware (n/a).
  - The runs are demonstrations on stein27 (pp. 13–16):
    - defaults: 0.73 s and 4,192 nodes;
    - rounding and shifting heuristics switched off: 0.75 s and 4,253 nodes;
    - aggressive heuristics: optimum found at the root, run interrupted by the user.
  - Performance claims are delegated to outside sources (p. 7):
    - competitive with commercial and non-commercial MIP solvers [22];
    - consistently one of the fastest non-commercial solvers for MIP in Mittelmann's benchmarks [38] and for PBO in the 2012 PB competition [46];
    - one of the fastest for nonconvex MINLP [33].
  - Performance variability is introduced with stein27: the instance has more than 2,000 optimal solutions, and time and nodes vary between installations. The reader is referred to MIPLIB 2010 [22] (p. 14).
- **D6 Positioning**:
  - The suite is positioned as non-commercial throughout: "one of the fastest non-commercial MIP and MINLP solvers" (abstract p. 3; pp. 5, 7).
  - Differences from commercial products:
    - branch-and-price through callbacks (p. 7);
    - Zimpl's LGPL source, against commercial modelling languages that cannot be given to colleagues or used in classes (p. 8).
  - Concessions are explicit: Zimpl implements "maybe 20% of the functionality of ampl", and freely available languages are "no match" for integrated commercial modelling systems (p. 8).
  - Lineage (pp. 5, 22):
    - CIP from Achterberg's thesis [1];
    - the MINLP extension from Berthold, Heinz and Vigerske [5] and Vigerske [33];
    - exact MIP from Cook, Koch, Steffy and Wolter [11];
    - the MIP background from Dantzig, Gomory, Land and Doig, Lodi, and *50 Years of Integer Programming*.
- **D7 Writing and rhetoric**:
  - Tutorial genre: each console transcript or code listing is followed by a reading of its output, for example what the display characters t, R and s mean, why two nodes are open, and how the LP time splits (pp. 13–16, 20–21).
  - The headline claim is repeated three times, each time with an external reference (pp. 3, 5, 7).
  - Concessions are given as numbers: "maybe 20%", a manual of "about 25 pages" (p. 8).
  - Hedging is low, and the outlook closes on "Citius, altius, fortius" (p. 22).
- **D8 Contribution and limits**:
  - Contribution: software documentation, an overview and tutorial of a released suite.
  - Stated limits are few:
    - the Matlab and Java interfaces are first or beta versions (pp. 10–11);
    - Zimpl's functionality is limited (p. 8);
    - the TSP model is limited in size, with a pointer to Concorde for larger instances (p. 12).
  - Future work (p. 22):
    - parallelization (a million cores [23], ParaSCIP [30]);
    - exact integer programming: floating-point solutions are "perfectly sufficient" for most commercial applications; exactness is crucial for particular classes, "especially feasibility problems", and desirable for research; a MIP solver that is exact in theory with practically acceptable times "remains an important task", with many open questions [11];
    - MINLP and CP integration;
    - more and bigger instances, solved faster.
  - Licensing: the ZIB Academic License with full source access. Source access is called a precondition for successful research (p. 21).

**Method links**:
- Method 5 ✅ evidence (group text): SoPlex is a double-precision solver by default, with long double optional, and offers iterative refinement, which "uses the gnu Multiple Precision Library and iterated floating point solves" to compute arbitrarily precise solutions (p. 10). The outlook keeps floating point as the default answer and reserves exactness for feasibility problems and research (p. 22).
- Method 5 ⚠ variant: Zimpl does all model-building arithmetic in rationals (p. 9). Exactness is placed at the cheapest stage, between data and model, and has nothing to do with any solver decision.
- Method 3 ✅ evidence (agenda, group text): exact integer programming is printed in 2012 as an open task with many open questions (p. 22). This is the ledger entry that the skill's Method 3 step 6 traces to SCIP 10.0 (2025).
- Not counted in the digest:
  - Taste 4 ✅: the "floating point otherwise" stance is already in print in 2012 (p. 22), and "proven" is defined as exact rational solving (fn. 10, p. 22).
  - Heuristic 4a ✅: a debug solution serves as oracle (p. 18).
  - Heuristic 5 ✅: the result files and the comparison script that the skill's later script fixes concern ship with the solver (p. 18).
  - Heuristic 3 ✅ in part: test coverage, asserts and static checks (p. 22).
  - "Already known" (build inside the open-source solver) ✅: source access is a stated precondition for research (p. 21). It is also the condition behind Method 1's limitation (needs source access).
- New-pattern candidate (existing name): *the release ships the measurement instruments*. The test target, per-instance result files with geometric means, a comparison script and the debug-solution check are all part of the distribution (p. 18).

**Transferable techniques**:
- [D4] Plant a known optimal solution in debug builds, so that any reduction, cut or propagation that removes it is caught at once (p. 18).
- [D4] Ship the test harness with the solver. One command runs a named test set under a named settings file and writes per-instance results with geometric means, and a script compares result files (p. 18).

### S039 · Learning and Propagating Lagrangian Variable Bounds for Mixed-Integer Nonlinear Programming (CPAIOR 2013, DOI 10.1007/978-3-642-38171-3_26)
**Read level**: full. The file is ZIB-Report 13-04 of January 2013, the preprint "to appear" in the CPAIOR 2013 proceedings (pp. 1, 3); differences from the published version were not checked. All 13 file pages were read: abstract, §§1–3 and conclusion (pp. 3–8), Table 1 (pp. 9–10; all 99 rows parsed by a script for the recount in D5), references (pp. 11–13). Figure 1 survives as axis labels and caption (p. 6), and Figure 2 as 20 bar counts and its caption (p. 7).
**Role**: core · **Coauthors**: Stefan Weltge, Otto-von-Guericke-Universität Magdeburg; Gleixner was at ZIB (p. 3). The two-author byline is alphabetical and contributions are not stated. The paper thanks Timo Berthold, Pietro Belotti and Domenico Salvagnin (p. 8) · **Position in trajectory**: The MINLP-component phase. This is the skill's [LVB13], the case behind Heuristic 9 ("duals of bound-tightening LPs become cheap one-row bounds"), implemented in SCIP 3.0 (p. 7). The OBBT line continues in INDEX S011 (J. Global Optim. 2017, "Three Enhancements for Optimization-Based Bound Tightening") and in the thesis (INDEX S032), whose OBBT and LVB results the skill cites under Taste 3 [Th pp. 145–147]. Neither was read in this batch.

- **D1 Problem and entry point**:
  - OBBT minimizes and maximizes each variable over a linear relaxation R and so gives the tightest bounds valid for R (problem (2), p. 4).
  - Domain reduction matters especially in MINLP, because smaller domains give tighter convex relaxations of the nonconvex constraints (p. 4).
  - A full OBBT round solves 2n LPs. Solvers therefore run it at the root, and in the tree only with limited frequency or according to its success rate (p. 4).
  - The entry point is to ask what the expensive OBBT solves can give "beyond simply obtaining tighter bounds". The dual solution proves the bound, and the proof can be kept as a globally valid inequality whose propagation approximates OBBT locally (the Contribution paragraph, pp. 4–5).
  - Transferable technique: when a component is rationed because it is expensive, ask what certificate its solves produce, and whether that certificate can be replayed cheaply where the component itself is not run (pp. 4–5).
- **D2 Core idea and algorithm design**:
  - **Lemma 1** (p. 5) has three ingredients:
    - the relaxation R = {x : a_iᵀx ≤ b_i} ⊇ X;
    - problem (3), max{x_k : x ∈ R, cᵀx ≤ z, x ∈ [ℓ, u]}, where z is an upper bound on the optimal value;
    - any dual-feasible λ, μ ≥ 0 with reduced costs r_j as in (4).
  - From these, U(ℓ, u, z) = Σ_{r_j<0} r_j ℓ_j + Σ_{r_j>0} r_j u_j + μz + λᵀb is a valid upper bound on x_k. For optimal multipliers it equals the OBBT bound.
  - The inequality (6) behind U is the Lagrangian variable bound (LVB) (p. 5).
  - **Remark 1** (p. 6): an LVB depends on the incumbent value when μ ≠ 0 and on the bounds of other variables when some r_j ≠ 0. It can therefore tighten x_k again after an improving solution or a bound reduction.
  - **The scheme** has three steps (p. 6):
    1. learn LVBs during one OBBT round at the root;
    2. propagate them locally whenever bounds on their right-hand side shrink through branching or propagation;
    3. propagate them globally after an improving solution.
  - **What changed against the closest prior idea**: Tawarmalani and Sahinidis [21] observed that any dual-feasible solution yields a one-row relaxation, which can tighten every variable in it. Applied unconditionally this "appears too expensive", so the paper keeps only the OBBT duals and tightens only the left-hand-side variable (p. 6).
  - **What did not change**: OBBT itself, whose LPs are solved anyway.
  - **Remark 2** sets the device's limits: LVBs are redundant aggregations of the rows of R, and "unlike MIP cutting planes, they are not designed to cut off the LP optimum". Adding them to the LP does not pay (p. 6).
  - Figure 1 shows an LVB learnt for a bound that OBBT does not tighten (pp. 5–6).
- **D3 Problem class and data model**:
  - The model is a MINLP (1) with a linear objective, without loss of generality: a nonlinear objective moves into a constraint f(x) ≤ x₀. The constraints g_i(x) ≤ 0 may be nonconvex, and the solver is spatial branch-and-bound over a convex relaxation (p. 4).
  - The correctness argument needs only LP duality over a linear relaxation R given by inequalities, together with an upper bound z on the optimal value; z is what lets the cutoff row enter (p. 5).
  - OBBT is applied only to nonbinary variables that appear in nonlinear constraints (p. 7).
  - Data: MINLPLib, after three exclusions (p. 7), leaving 211 instances:
    - 18 instances that SCIP 3.0 cannot parse or handle (named in fn. 1);
    - 41 that are linear after presolving or solved at the root before OBBT runs (named in fn. 2);
    - gear4 and nvs22, "for which SCIP 3.0 returned a wrong solution value".
- **D4 Algorithm and implementation design**:
  - Proof device (proof of Lemma 1, p. 5): multiply the rows of (3) by their duals and aggregate them to (Σ λ_i a_i + μc)ᵀx ≤ λᵀb + μz. With the reduced costs this becomes x_k ≤ Σ r_j x_j + μz + λᵀb, and the right-hand side is then bounded over the box. Equality for optimal multipliers follows from complementary slackness.
  - Implementation (p. 7):
    - one OBBT round at the root after the first separation loop, minimizing and maximizing each eligible variable once over the LP relaxation;
    - the bounds of the variable being optimized are relaxed "slightly", so that a nontrivial LVB becomes more likely when OBBT does not tighten the bound;
    - LVBs are stored and propagated "in a suitable topological order whenever their right-hand side improves".
  - Local or global propagation follows the trigger: a bound change propagates locally, an improving solution globally (p. 6).
  - The OBBT round has no effort control, such as an LP iteration limit. This is stated as part of the setup and used to explain the timings (p. 8).
- **D5 Computational evaluation**:
  - Two stated aims (p. 7):
    1. count how many nontrivial LVBs (μ ≠ 0, or r_j ≠ 0 for some j ≠ k) OBBT yields;
    2. measure what propagating them does.
  - Setup: SCIP 3.0 with CPLEX 12.4, CppAD and Ipopt 3.10.2, on Xeon X5672 3.2 GHz nodes with 48 GB (p. 7).
  - (i) Figure 2: every instance obtained LVBs from at least 15% of its OBBT LPs, and 132 of 211 instances from more than half (p. 7). Reader's check: the 20 extracted bar counts sum to 211, and 132 of them lie above 50%.
  - (ii) The performance run compares OBBT alone with OBBT plus LVB propagation, with a 1 h limit (pp. 7–8). To "reduce distorting side effects" of the tree search, it switches off heuristics in the tree and conflict analysis, and uses first-index branching with depth-first node selection.
  - Outcomes (p. 8):
    - two more instances solved with LVBs, one lost;
    - 94 instances timed out in both runs and 109 were solved by both;
    - after dropping ten easy instances solved at the root, 99 remain, on which LVBs cut the shifted geometric mean of nodes by 14% and of time by 7%;
    - the shifts are 5 s and 100 nodes, defined with a rationale in fn. 3.
  - A control run with SCIP defaults, "For validation", gives −12% nodes and −6% time on the instances solved by both. Their number is not given (p. 8).
  - LVB propagation took at most 2% of the running time, except on two easy instances (p. 8).
  - The smaller time gain is put down to longer root processing, made worse because the OBBT round had no effort limit (p. 8).
  - Table 1 prints every instance with nodes, time, LVB time and relative differences (pp. 9–10).
  - **Reader's recount from the 99 rows** (pp. 8–10):
    - (a) The relative changes are reproduced: −14.2% nodes, −7.0% time. The printed means (1,423 → 1,222 nodes; 8.27 → 7.69 s) are matched exactly only after adding one instance with 1 node and 0.10 s. The 99 rows alone give 1,465 → 1,257 and 8.39 → 7.80, so the mean row seems to cover 100 instances (p. 10).
    - (b) The outcome counts sum to 206 of 211 (2 + 1 + 94 + 109; p. 8): five instances are not accounted for.
    - (c) The time gain is carried by a few instances. Without ortez, ex1244 and csched1 (−97.8%, −96.8% and −80.2%), it becomes +0.3%. Trimming the three largest changes on each side leaves −2.4%. Time is lower on 32 instances, higher on 26 and equal on 41. On the 23 instances that take at least 10 s in one of the two runs, the reduction is 16.8% (pp. 9–10).
    - (d) Large losses stand in the table without comment in the text: enpro56 +1,161.4% nodes and +89.9% time; ex1252a +507.5% and +280.8% (532 s → 2,028 s); ex1265 +199.5% and +91.1% (pp. 9–10).
  - No significance test, seeds or permutations.
- **D6 Positioning**:
  - OBBT's lineage (p. 4):
    - Quesada and Grossmann 1993 as the first appearance "we are aware of";
    - generic global optimization codes;
    - Zamora and Grossmann's branch-and-contract with an objective cutoff;
    - the solvers αBB, Couenne, GloMIQO, LaGO and SCIP;
    - Caprara and Locatelli's theory of iterated OBBT.
  - The principle of reusing dual-feasible solutions for bound tightening is credited to Tawarmalani and Sahinidis [21]. The paper claims only a selection rule on top of it (p. 6).
  - Prior work is restated, not criticised.
- **D7 Writing and rhetoric**:
  - A short paper with about six printed pages of text, built from:
    - a labelled "Contribution." paragraph (p. 4);
    - one lemma with a short proof (p. 5);
    - one two-variable example (pp. 5–6);
    - two remarks that mark what the device is for (p. 6);
    - a three-step scheme (p. 6).
  - The claims use strong words without a test: LVB propagation "helps to speed up the solution process significantly" (p. 5), and "the achieved savings are substantial" for a single propagator (p. 8). The conclusion reports "more than 10%" fewer nodes, "on affected instances" (p. 8).
- **D8 Contribution and limits**:
  - Contribution layers: a concept (the LVB), a lemma, an implementation in SCIP, and a computational study on MINLPLib (pp. 4–8).
  - Printed limit: the time gain trails the node gain, because the root takes longer and the OBBT effort is not controlled (p. 8).
  - Future work (p. 8): does LVB success correlate with the tightness of the OBBT LP that generates it, and how do LVBs behave together with a more sophisticated OBBT implementation?
  - Not stated (reader): the five instances missing from the outcome counts, the concentration of the time gain on three instances, and the large individual slowdowns (D5).

**Method links**:

- Not counted in the digest:

  - Heuristic 8 ⚠, in part:

**Transferable techniques**:
- [D2] Keep the dual multipliers of an auxiliary LP that you solve anyway as a learnt inequality x_k ≤ Σ r_j x_j + μz + λᵀb. Re-evaluate its right-hand side over the current box whenever a bound on the right-hand side or the incumbent improves (Lemma 1, Remark 1, pp. 5–6).
- [D2] Make a known but too expensive idea affordable with a selection rule: which duals to keep (OBBT's) and in which direction to propagate (the left-hand-side variable only) (p. 6).
- [D4] Relax the bound of the variable being optimized slightly, so that the dual still yields a nontrivial inequality when the bound itself does not move (p. 7).
- [D4] Propagate learnt bound inequalities in topological order, and only when a quantity on their right-hand side improves (p. 7).
- [D5] Test a propagator in a setting that freezes the components it interacts with (no tree heuristics, no conflict analysis, first-index branching, depth-first search). Then rerun with defaults as a control and print both results (pp. 7–8).
- [D5] Before reporting the effect, report how often the component produces something nontrivial (the rate per auxiliary LP, as a histogram over instances) and its own share of the running time (pp. 7–8).
- [D7] Say in a remark what the device is not (not a cut, not for the LP), so that readers judge it as what it is (Remark 2, p. 6).

- **D1 Problem and entry point**:
  - Primal heuristics are a substantial ingredient of MIP solvers, and MINLP research shows an "increasing interest in general-purpose primal heuristics" (p. 3).
  - Undercover is designed as a start heuristic inside a complete solver such as Baron, Bonmin, Couenne, GloMIQO, Minotaur or SCIP (p. 4).
  - The design brief comes from that use (p. 4):
    - standalone heuristics aim at success on as many instances as possible;
    - inside a solver the overall performance counts, so a few successes are worth trading for average running time;
    - hence a "fast fail" strategy that takes the crucial decisions early and defensively.
  - Two distinctions (p. 4):
    - Undercover is not an extension of a MIP heuristic and has no MIP counterpart;
    - it solves a fixed number of auxiliary problems (two MIPs and at most two NLPs), not a sequence whose length depends on the instance.
  - Transferable technique: derive a component's design brief from where it will run (inside a complete solver: average time, abort early) before designing it (p. 4).
- **D2 Core idea and algorithm design**:
  - **The insight** (p. 5): integrality is a special case of nonconvex nonlinearity, since a bounded integer is a root of a polynomial. In MINLP "easy" therefore means few nonlinear constraints.
  - Fixing a suitable set of variables can make every constraint linear, and then each solution of the resulting sub-MIP is feasible for the MINLP (p. 5).
  - LNS heuristics for MIP (RINS, DINS, RENS, local branching) fix many integer variables to get an easy problem of the same class. Undercover instead fixes as few variables as possible to change the class (pp. 5, 7).
  - **Theory**:
    - A cover is defined on the constraint functions (Definition 2.1, p. 5).
    - Theorem 3.3: C is a cover if and only if it is a vertex cover of the co-occurrence graph built from the Hessian sparsity patterns (pp. 7–8).
    - Corollary 3.4: computing a minimum cover is NP-hard, even for quadratic constraints (p. 8).
    - The covering binary program (4) is nevertheless solved exactly. The "complicating variables" of a bilinear program, or any greedy minimal cover, can be arbitrarily larger than a minimum cover (Example 3.5, Figure 3, pp. 8–9).
  - **The algorithm** (Figure 4, p. 12; pp. 9–13):
    1. Fix the cover variables one by one to rounded and projected reference values, with domain propagation after each fixing.
    2. On an empty domain, backtrack one level, try alternative values and run conflict analysis.
    3. Solve the sub-MIP.
    4. If the sub-MIP is solved or proven infeasible and all cover variables are integer, add a no-good on the cover assignment.
    5. Polish the solution with an NLP over the continuous variables.
- **D3 Problem class and data model**:
  - The model is a MINLP (1) with a linear objective and L_i < U_i, both without loss of generality (p. 4). §3 assumes twice continuously differentiable constraint functions and remarks that the idea extends to general MINLP (p. 7).
  - The cover depends on the formulation, not on the feasible set (p. 5).
  - Sparsity patterns from algorithmic differentiation depend on how a function is written: x³ + 3x² − (x+1)³ is linear but may show structural nonzeros. Functions are therefore simplified during presolve. Computational graphs are required; oracle-based evaluation is not enough (p. 11).
  - Test sets (p. 14):
    - Root comparison: 147 MIQCPs. These are the 172 of Misener and Floudas's test suite minus 7 very easy instances (solved by presolving or the root LP), 11 nuclear instances with an unbounded root LP, and 3 LeeCrudeOil instances on which Bonmin did not stop.
    - MINLP comparison: 110 MINLPLib instances that are not MIQCPs, remain nonlinear after presolve, contain no sin or cos, and have a bounded root LP.
    - In-solver run: 149 instances, the 147 plus the three LeeCrudeOil instances minus ruiz_flowbased_pw4, on which SCIP stops with an error.
  - Reader's count: 172 − 7 − 11 − 3 = 151, not 147. Table 3 has 171 rows and contains 15 nuclear instances that do not appear in Table 2 (pp. 23–29), so "eleven" (pp. 14, 16) appears to be fifteen.
- **D4 Algorithm and implementation design**:
  - **Proof devices** (pp. 7–9):
    - restricted to the unfixed variables, a function has as Hessian the corresponding principal submatrix of its Hessian, and a C² function is affine if and only if its Hessian vanishes; hence a cover is the same as a vertex cover;
    - NP-hardness: any graph is the co-occurrence graph of min{0 : x_i x_j ≤ 0};
    - a bipartite counterexample shows that minimal (not minimum) covers can be arbitrarily large.
  - **Implementation** (pp. 11–14, 17):
    - Edges come from the constraint structure or from algorithmic differentiation (p. 11).
    - The covering problem is solved at the root node only, and a greedy start heuristic guarantees that an incumbent always exists (p. 11). A secondary SCIP instance solves it (p. 13).
    - Fix-and-propagate calls the solver's own domain propagation and conflict analysis (pp. 11, 13).
    - The one-level backtrack tries a fixed list of alternatives, each value at most once (p. 11):
      - 1 − X_i for binaries;
      - L_i, then U_i, for other variables;
      - X_i − |X_i| and X_i + |X_i| when a bound is infinite;
      - −1 and +1 when X_i = 0.
    - The sub-MIP is solved by a secondary SCIP (pp. 13–14) with a hard limit of 500 nodes and a dynamic stall-node limit of 1 to 500. Expensive presolving is off, the "primal heuristics emphasis aggressive" and "emphasis feasibility" settings are on, and expensive pre-root heuristics and components that solve sub-MIPs themselves are off.
    - The LP solution is the reference point (p. 13).
    - Incumbent values serve as fixing alternatives, which makes the sub-MIP feasible (after Danna et al.), and a primal cutoff restricts the sub-MIP to improving solutions (p. 17).
  - The learnt constraints change only the global solve, not Undercover's own run (p. 13).
  - Variants ruled out in preliminary experiments became user parameters (p. 13). Aggressive options are kept in footnotes 2–3 (pp. 10–11).

**Transferable techniques**:

- [D2] Solve an NP-hard selection subproblem exactly, but only at the root, with a greedy incumbent as fallback. Do it after showing that greedy minimal choices can be arbitrarily bad (pp. 8–9, 11).
- [D4] Fix variables one at a time with propagation after each fixing. Move a value that has left its domain to the nearest bound, backtrack one level over a short list of alternatives, and abort if that fails (pp. 9–12).

- [D5] Evaluate a heuristic twice. First alone at the root against other solvers' root nodes, counting the instances where it beats each. Then inside the default solver with and without it, one job per node (pp. 14–17).
- [D7] Put the problem class on which the method fails into the abstract (p. 3).
